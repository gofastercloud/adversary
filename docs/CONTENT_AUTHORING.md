# Content authoring (schema v2)

Everything the game shows is data. `npm run validate` (also part of `npm test`) enforces everything below, including that
every MITRE, EMB3D, CTID and D3FEND id exists in the offline datasets, so a bad reference fails the build, not a player.

## Layout

```
content/core/*.json        generated by scripts/gen-*.mjs  (taxonomy, cards, relics, doctrines, events, tuning, achievements, adversary-meta)
content/packs/<id>.json    generated by scripts/gen-packs.mjs from scripts/packs/<id>.mjs
scripts/packs/<id>.mjs     the file you edit: exports base, overrides, cards, relics, systems, ttx
data/                      real datasets (see DATA_SOURCES.md); never hand-edit
```

Edit the `.mjs` source, run `node scripts/gen-packs.mjs <id>`, then `npm run validate`. `gen-packs` keeps the header of an
existing pack JSON and replaces the rest; **delete `content/packs/<id>.json` if you change `base`** (assets, roster, org).

## References (`refs`)

Compact `source:id` strings resolved by `engine/refs.js` to a labelled deep link. Unknown source or id fails validation.

| Source | Example | Checked offline |
|---|---|---|
| `attack` | `attack:T1078.004`, `attack:M1032`, `attack:G1017`, `attack:C0030`, `attack:A0003` | yes (techniques, mitigations, groups, campaigns, software, assets) |
| `ics` | `ics:M0811` | yes |
| `emb3d` | `emb3d:MID-040`, `emb3d:TID-201` | yes |
| `ctid` | `ctid:aws`, `ctid:nist` | set name |
| `d3fend`, `capec`, `cwe` | `cwe:639` | d3fend yes |

## Cards

```js
{ id: 'ot.chem-interlock', name, type: 'control' | 'action' | 'policy' | 'augment',
  fn: 'protect', prop: 'tampering', cost: 2, rarity: 'common|uncommon|rare', target: 'asset|control|foothold|none',
  ward: { T: 2 },                  // STRIDE letters S T R I D E
  mit: ['M0812'],                  // ATT&CK mitigation ids: +1 ward vs techniques that list them
  cov: { protect: { T1078: 2 }, detect: {} },   // CTID-style scored coverage (1-3)
  detect: { str: 3, n: 1, scope: 'asset|global' },
  aegis: { revive: 4 }, flags: ['segment'], fx: [{ op: 'isolate' }], consume: 'battle|run',
  base: ['protect.tampering'],     // augments: which control cells they fit
  aug: { ward: { E: 1 }, resists: ['T1621'], expert: [{ tech: 'T0858', ref: 'emb3d:MID-031' }] },
  desc, lesson, refs }
```

Rules the validator enforces: augments' `resists` must be backed by an ATT&CK mitigation in `aug.mit` (otherwise use
`expert` with a citation ref); actions need `fx` (ops are listed in `scripts/validate-content.mjs`); only actions can be
consumables; every card needs a `lesson` and refs.

## Scenario pack

`base`: `id, name, version, tagline, icon, theme{accent,accent2,bg[3]}, org{name,sector,brief,crownJewels[],regimes[{name,note,refs}]}`,
`assets` (6-9; at least two crown jewels, each two or more hops from an exposed asset), `roster.acts[3]`
(`battle[]`, `elite[]`, `boss`, `tiers{}`; every id needs `data/adversaries/<id>.json` and an entry in adversary-meta), `reading[]`.
Asset kinds: `email endpoint identity server data app cloud backup vendor ot`.

`overrides`: sector skins for the 36 matrix cells (`name` ≤44, `flavour` 8-52, `desc` 60-420, 2-6 refs). Mechanics never change.

`systems` (data-flow diagrams for the Whiteboard): 5-9 elements on the 1000×560 canvas (≥190 px horizontal or ≥100 px vertical
between centres), 6-12 flows, optional boundaries, **8 scenarios** with an unambiguous STRIDE `answer`, a `why`, and refs.
Flow scenarios may only answer T, I or D (spoofing, repudiation and elevation apply to elements). At least two flow and two
store scenarios, at least five distinct letters.

`ttx`: `{ id, name, blurb, adversary{id,tier}, rounds 4-12, maxScore, injects[], objectives[] }`. Injects: `round, at, kind, title, text, fx[]`
and optional `decision{prompt, choices[2-4]}` with one `best`, `quality: best|good|ok|poor`, `fx`, `lesson`, `refs`.
Objectives: `keepJewel, detectBy, evictAll, resilienceAbove, win, decisions`.
`node scripts/gen-ttx-draft.mjs <flow-id> --adv <id>` drafts one from a real incident in `data/flows`; the decisions it
writes are skeletons for you to refine.

## Adding an adversary

1. ATT&CK group or campaign: add its id to `ROSTER` in `scripts/build-attack-data.mjs`, run `npm run data`.
2. Not in ATT&CK yet: add it to `scripts/build-custom-adversaries.mjs` with cited sources (TeamPCP is the example). Technique
   mappings must be ones the cited vendors state; do not record IPs, hashes or domains.
3. Add a meta entry (`scripts/gen-adversary-meta.mjs`): tier, role, blurb, traits (documented behaviour as a game rule), **goal**,
   optional `assessed` techniques (labelled as assessed intent in the UI), then `node scripts/gen-adversary-meta.mjs`.

## Writing good lessons

One idea per lesson, with the failure mode first. Say what is legally required (SOCI, CPS 234, Privacy Act) separately from
good practice. Prefer real incident detail with a citation over generic advice. Keep Australian spelling.
